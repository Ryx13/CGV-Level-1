# Deadway City — Level 1

A playable first level built around the outbreak story: fight through the
infested main street, break off east into the depot yard to recover the
cure's last ingredient, then get it back to extraction — on-foot zombie
combat (gun + melee) and a physics-driven drivable car, against a
spawning/chasing horde.

## Level 1 structure (3 stages)
1. **Clear the route** — fight down the main street. Neutralize 10 infected
   to open the way east.
2. **Recover the sample** — a signpost partway down the street points
   toward the depot yard, off the main road to the east. It's a small
   fenced compound with its own buildings, guarded by four tougher
   "stabilized-but-still-dangerous" infected. Walk up to the amber marker
   to secure the sample.
3. **Extract** — the green ring near the north end of the street lights up
   once you have the sample. Get there (on foot or by car) to win.

## The core combat twist (from the story)
Gunfire and melee stagger an infected down rather than deleting it outright
("stabilized," matching the story's premise that these aren't ordinary
zombies) — knockdowns count toward your objective immediately. Left alone
for several seconds, a downed one gets back up and keeps hunting, so it's
still worth a fast follow-up hit if one's near you when it drops — but
you're never blocked on a required "finishing" step you weren't told
about.

## Run it (required — do not just double-click index.html)

Browsers block a plain `file://` page from loading the `.glb` model files
(CORS), so you need a tiny local server. From **this folder**, run one of:

```bash
# Python (usually already installed)
python3 -m http.server 8000

# Node
npx serve .
```

Then open **http://localhost:8000** in Chrome or Edge (desktop). That's it —
everything else (buildings, road, car, HUD) is generated by the code, no
build step needed.

## Controls
- **WASD** — move / drive
- **Mouse** — look around / aim
- **Left Click** — shoot
- **Right Click** — melee
- **Shift** — sprint
- **Ctrl / C** — crouch (slower, quieter, lower camera — no sprinting while crouched)
- **Space** — jump (on foot) / handbrake (driving)
- **F** — enter / exit the car (walk up to it first)
- **R** — reload
- **Esc** — release the mouse cursor

## What's actually simulated (not faked)
- **Car physics** uses `cannon-es`'s raycast vehicle: real suspension per
  wheel, engine force on the rear wheels, front-wheel steering, and brake /
  handbrake — so it drifts, bottoms out on rough ground, and reacts to
  ramming zombies based on actual speed, not a scripted animation. The
  body mesh is anchored to the wheels' actual contact points each frame,
  not the physics chassis origin, so it can't visually float off the tires.
- **Player movement** is a physics body (gravity, collision with buildings
  and boundary walls), not a fly-cam. Movement and the chase camera both
  derive from the same `forwardFromYaw` / `rightFromYaw` helpers so they
  can't drift out of sync with each other again.
- **Zombies** run a small state machine (idle → chase → attack → dead) and
  randomly pick one of three uploaded rigged variants
  (`zombie_walker.glb` has a `walk_relaxed` clip; the other two are static
  poses that still move/root-motion but don't limb-animate), all
  normalized to the same height, with a procedural low-poly fallback if
  none of those files load. Open the browser console to see the computed
  scale factor logged per variant if sizing ever looks off again.

## Fixes in this revision
- Zombies were rendering oversized ("titans") — likely a knock-on effect of
  the camera bug below putting the camera far too close to characters. The
  scale computation now also has a sane clamp and logs its numbers to the
  console so this is easy to verify directly.
- The chase camera was placed in *front* of the character instead of
  behind, so you saw their face and movement read as inverted (forward
  walked you toward the camera, strafing was mirrored). Fixed by deriving
  the camera position from the same forward/right vectors movement uses,
  on the correct side.
- The car body mesh tracked the physics chassis origin, which sits above
  true ride height once the suspension compresses — it now anchors to the
  wheels' actual ground contact instead, so it can't float.

checksum) that build -D really was what was being tested — since the
symptoms persisted in a build I'd verified was correct, the previous
fixes must have been individually correct but incomplete. This surfaced
one real root cause behind two separate complaints at once:

- **Gun still huge + still can't run, together**: the player's
  third-person body was secretly being swapped to `zombie_walker.glb` —
  the *same rigged model used for zombies* — once it finished loading,

  from one cause: (1) that model's only animation clip is a zombie
  shamble, so "sprint" was always just the shamble sped up — no amount of
  speed-constant tuning could make a shamble clip look like running,
  because the clip itself was never a running gait; (2) the zombie mesh
  gets rescaled to match human height on load, and the gun, parented to
  a bone inside that scaled rig, inherited the same scale-up — likely
  the actual reason it kept looking oversized even after being resized
  in code. Disabled that reassignment entirely; the player now uses the
  procedural body throughout, with its gun at normal, unscaled size.
- **"Still can't run"**: with the above fixed, also gave the procedural
  walk-cycle an actual running gait instead of just a faster walk cycle —
  wider leg swing, opposite-arm counter-swing, and a forward torso lean,
  all scaled to sprint state specifically (previously only the cycle
  speed changed, not the motion shape).

## Changelog — latest pass (build -L)
- **Car wheels lying flat**: real bug, found it — the wheel mesh's
  rotation was set once at creation (`rotation.z = Math.PI/2`), but every
  frame the code overwrites that same mesh's quaternion wholesale with
  the physics engine's wheel transform, silently discarding the
  correction. This bug has likely existed since the very first version —
  it just stayed invisible before because the old car model had its own
  wheel-rotation bones, which hid the procedural wheel cylinders
  entirely. The new truck has no such rig, so the cylinders became
  visible for the first time and exposed it. Fixed by baking the
  rotation into the geometry itself instead of the mesh's transform, so
  it survives having a different quaternion applied every frame.
- **Player still smaller than zombies**: rather than guess a 4th number,
  the debug readout (bottom-left) now shows the player's actual height
  in meters directly next to the zombie reference height, so it can be
  dialled in with **[** / **]** against a real target instead of by feel.
  Also bumped the starting default further (0.4 → 0.55) based on the
  trend so far.
- **Gun position**: no code bug found on review — the hand-tracking
  logic is internally consistent, so this is most likely just an
  unverified grip preset (see build -K's note: the pistol's real
  orientation is unknown without rendering it). Please cycle **U** and
  tell me the number that looks closest, or exactly how it's wrong
  (upside down, backwards, etc.) if none do.
- **World detail**: added a few purely decorative crates near the depot,
  reusing the already-loaded crate model (no extra download) rather than
  adding new assets, consistent with keeping performance in check.

## Changelog — build -H
**Important process note first**: I discovered mid-pass that my syntax-

entire project — Node stops validating a plain `.js` file for real errors
once it sees a top-level `import` statement (which this file has always
had, since it's written as an ES module for the browser), and just
reports success regardless of what's actually in the file. I confirmed
this converts even deliberately-broken garbage into a false "OK". Every
"syntax OK" I've reported in this conversation was this false positive —
harmless when the code happened to be valid anyway, but not the
verification I thought it was. Fixed by piping through
`node --input-type=module --check` instead, which actually works. This
also caught a real typo (a stray `#` from a comment I mistyped) before it
shipped, which it would previously have missed entirely.

  looks exactly like "the world stopped rendering." Roughly halved
  streetlight count, removed one particularly expensive 60-radius point
  light at the depot (kept the visual glow, dropped the light itself),
  and eased fog density slightly (the wider street pushes buildings
  further out, so more of them were fading into fog than before).

  Additionally slowed stamina drain and sped up regen — at the old rates
  a held sprint cut out after ~5s and took ~6s to refill, which held
  continuously (the natural way to test "can I run") reads as "sprint
  stopped working" rather than "temporarily depleted."

## On "world still blocky" — the honest limit of this approach
Every building, car, and prop in this game is built from primitive boxes/
cylinders at runtime, with procedurally-drawn canvas textures. That
approach can be pushed further (as this pass did with rooftop setbacks),
but it fundamentally cannot stop looking like primitives-with-detail,
because the base geometry never stops being a box. Actually fixing this
means importing real modeled assets (.glb/.gltf) instead of building
shapes in code — the same pipeline already used for the zombie models.
The free option the "how to make a web game" article itself recommends is
[Kenney.nl](https://kenney.nl) — City/Cyber City/Vehicle asset packs are
CC0, sized for exactly this kind of low-poly urban scene, and would drop
into `assets/` the same way `zombie_walker.glb` already does. If you
download a pack and share the files, I can wire them in to replace the
procedural buildings/cars directly — that's a real fix, not a bigger box.
